## 一、打标请求「请求须使用 JSON 格式」——已修复

### 结论

前端 `prepareImportSummary()` 发 POST 时**没有设置 `Content-Type`**，被服务端的 JSON 强制校验拦掉。

### 链路

1. 点「开始打标」→ `openImportModal(id)` → `if(pending) prepareImportSummary(id)`（`index.html:2553`）
2. `prepareImportSummary` 里 `fetch('/api/imports/{id}/prepare',{method:'POST'})`，**无 headers、无 body**
3. 服务端 `app.py:227` 前置校验：
   ```python
   if method == "POST" and self.headers.get_content_type() != "application/json":
       return self.send_json(415, {"ok": False, "error": "请求须使用 JSON 格式"})
   ```
4. 浏览器不带 `Content-Type` 时，Python `email.message.get_content_type()` 默认返回 `text/plain` → 判定失败 → 415

### 实测证据（curl 三组对照）

| 请求写法 | 响应 |
|---|---|
| `POST` 不带 `Content-Type` | **415** `{"ok":false,"error":"请求须使用 JSON 格式"}` |
| `POST` + `Content-Type: application/json` | 进入业务逻辑（返回 404「找不到这条导入记录」，因为用的是假 id） |
| `POST` + `Content-Type: text/plain` | **415** 同上 |

### 修复

`deploy/show-v2/index.html` 与 `versions/feedback/modules/news/prototype/index-core.html` 各一处：

```js
// 修复前
const response=await fetch(`/api/imports/${id}/prepare`,{method:'POST'});
// 修复后
const response=await fetch(`/api/imports/${id}/prepare`,{
  method:'POST',headers:{'Content-Type':'application/json'},body:JSON.stringify({})
});
```

### 修复后浏览器实测

构造一条 `status=pending` 的导入记录，点「开始打标」，用 CDP 抓包：

```
请求：POST /api/imports/diag-1/prepare
      Content-Type: application/json
      body: {}
响应：502
弹层：新闻链接暂时无法解析，请检查链接是否可公开访问。
JS 异常：无
```

502 是因为测试用的是 `example.com` 假链接，抓不到正文，**属预期**；关键是从 `415` 变成了正常业务流程。

### 全项目扫描结果

前端共 4 处 POST，只有这一处缺 header：

| 位置 | 用途 | Content-Type |
|---|---|---|
| `index.html:2405` | 新建导入记录 | ✅ application/json |
| `index.html:2524` | **生成摘要（本次修复）** | ✅ 已补 |
| `index.html:2575` | 确认入流 | ✅ application/json |
| `index.html:2638` | AI 分析 | ✅ application/json |

`DELETE /api/imports/{id}` 不受影响，因为校验只针对 POST。

## 二、iFinD 新闻「只有几条、只有两天、当天没有」

### 2.1 管线结构：五道收窄

| 环节 | 规则 | 位置 |
|---|---|---|
| ① 日期范围 | 今天 + 前 6 天 = 7 天 | `news_provider.py:201` `recent_dates()` |
| ② 关键词 | 每天 3 国内 + 6 国际 + 3 补充 = 12 个，每个 `size:20` | `:24-41`、`:657` |
| ③ 每日上限 | 每天只取 `min(条数, 20)` | `:680-681` |
| ④ DeepSeek 质量门槛 | 必须同时满足：`content_type=="事实新闻"`、`quality_score 70–100`、`factuality 4–5`、`materiality 3–5`、`a_share_relevance 4–5`（或 3 + 宏观/行业 + `core_event`≥6 字 + 有 `impact_targets`）、`reject_reason` 为空 | `_passes` `:376` |
| ⑤ 事件去重 | `core_event` 相似度 ≥0.72 且（同日或同主体）→ 合并为一条 | `_event_dedup` `:426` |

第 ④ 道是最严的一关。例如一条"某券商建议关注某某板块"的研报，会因 `reject_reason="以观点、预测或投资建议为主"` 被直接丢弃（`:357`）。

### 2.2 决定性因素：175 秒总预算（抓取与摘要共用）

```python
deadline = time.monotonic() + 175     # :636
...
if left < 2: break                    # :650 抓取阶段耗尽即停
left = deadline - time.monotonic()    # :526 摘要阶段复用同一个 deadline
```

7 天 × 12 关键词 = **最多 84 次 iFinD 调用**，加上若干批 DeepSeek 摘要，全部挤在 175 秒内。平均每次可用时间只有 2 秒出头。

### 2.3 量化模拟（虚拟时钟，不真实等待）

用项目真实的 `NewsProvider._refresh()`，替换掉时钟与外部调用，模拟不同接口延迟下的结果：

| iFinD 单次耗时 | 覆盖日期 | 候选条数 | 最终入库 | 摘要处理失败 |
|---|---|---|---|---|
| 1.5 s | 7 / 7 | 140 | 19 | 0 |
| 3 s | 7 / 7 | 132 | **3** | **120** |
| 4 s | 0 / 7 | — | — | 整次失败 `timeout` |
| 6 s | 4 / 7 | 66 | **3** | 54 |

> 表中的"最终入库"仍含事件去重的贡献（模拟数据的标题高度相似，真实数据会更分散）。关注点是**候选数与入库数的落差**。

三条可复现的规律：

1. **单次约 3 秒**：抓取吃掉大部分预算，摘要阶段 120/132 条来不及处理 → 只剩 3 条。**这是"只有几条"最可能的机制。**
2. **单次约 4 秒**：整次抓取触发 `timeout`，`ok:false`，前端回退到示例数据 → 表现为"完全没有真实新闻"。
3. **单次 6 秒**：只覆盖前 4 天，后 3 天候选为 0，且摘要仍只剩 3 条。

### 2.4 "当天没有"是另一个独立问题

关键事实：`dates[0]` 就是今天，**抓取顺序今天优先**。所以预算不足应该先影响最早的日期，而不是今天。当天为 0 另有原因，有三种可能：

| 候选 | 特征 | 判断方法 |
|---|---|---|
| **A. `time_start=time_end=日期` 的语义** | 若接口把 `time_end=2026-11-04` 按 `00:00:00` 解释，当天区间为 `[00:00, 00:00]`，当天必为空 | 把 `time_end` 改成 `'2026-11-04 23:59:59'` 对比条数 |
| **B. 数据源当天收录延迟** | 两种写法当天都是 0 条 | 同上，均为 0 |
| **C. 时间解析后不属于当天** | 接口返回了，但 `published_at[:10]` 不等于今天，被 `:667` 的硬过滤丢弃 | 比较"解析条数"与"同日条数"的差 |

### 2.5 一步定位：`diag_news.py`

已新增 `deploy/show-v2/diag_news.py`，对最近 3 天（或 `--all-days` 七天）**各跑两种参数写法**并对比：


输出示例结构：

```

  现状 time_start=end=日期     返回  0 条，同日  0 条，耗时 2.31s
  全时段 00:00:00~23:59:59     返回 18 条，同日 17 条，耗时 3.02s

```

脚本末尾会自动给出判定：

- 现状 0 条、全时段 >0 条 → 根因是 `time_end` 语义，给出修改行号

- 有"被日期过滤丢掉 N 条" → 时间格式/时区问题
- 同时打印单次平均耗时，并算出 175 秒预算实际能覆盖几天

脚本只读，不写文件、不动缓存、不影响正在运行的服务。每次最多 3~7 组 × 2 次调用。

按性价比排序，**我没有改这些**（属后端取数逻辑，需与负责同学确认）：

### 2.7 前端可做的两件事

1. **把统计暴露出来**：`/api/news` 已返回 `processing_stats`，含 `candidate_by_date`、`quality_rejected`、`processing_failed`、`final_count`。在导入页或状态提示里显示一行"抓取 132 条 · 通过 3 条 · 处理失败 120 条"，就能让"少"变成可解释的数字，而不是黑盒。
2. **状态标签区分来源**：顶栏现在只有「● 示例数据」/「● 实时」。建议增加「缓存（X 分钟前）」一档，因为 `fallback_reason` 为 `recent_cache` / `refresh_busy` / `timeout` 时页面拿到的是旧数据，用户无法分辨。
