## 二、数据接入同学

### 2.1 先花 5 分钟定位原因

改代码前必须先判断是哪一类问题，否则改了半天可能改错地方。

```powershell
cd deploy/show-v2
set IFIND_MCP_AUTHORIZATION=你的授权串
python diag_news.py
```

脚本只做只读查询，不写文件、不动缓存，每次消耗 3~7 组 iFinD 额度。看输出里 `time_end` 两种写法的返回条数：

- **A 类**：`time_end 23:59:59` 明显比 `time_end 当天 00:00:00` 多 → 当天数据能恢复，优先做第 1 条
- **B 类**：两种写法都少 → 是预算分配问题，优先做第 2、3 条

加 `--all-days` 探测全部 7 天，加 `--raw` 打印原始返回片段。

### 2.2 五项改动（按性价比排序）

| # | 改什么 | 位置 | 改完的收益 |
| --- | --- | --- | --- |
| 1 | `time_end` 从 `day` 改成 `day + " 23:59:59"` | `news_provider.py:657` | A 类问题下当天数据立刻恢复 |
| 2 | 抓取预算按天分配（175s ÷ 7 ≈ 22s/天），单日超时跳到下一天 | `_refresh` 循环 | 保证 7 天都有机会，不会前几天慢就把后面全饿死 |
| 3 | 抓取与摘要分开计时（建议 110s + 65s） | `:636`、`:526` | 避免抓取吃光摘要时间，导致 120 条 `processing_failed` |
| 4 | 每日候选上限 20 → 10 | `:680-681` | 摘要压力直接减半 |
| 5 | 摘要失败时降级入流（标 `summary_status="pending"`）而不是丢弃 | `_summarize` `:551` | 候选不会因模型超时凭空消失 |

**第 5 条效果最直接，但会改变「没过质量审核就不展示」的产品原则，需要先跟全组确认再动。**

### 2.3 改完怎么验证

1. 清空缓存目录 `deploy/show-v2/data/` 后重启服务
2. 打开页面快讯流，看是否 7 天都有数据、当天有数据
3. 看 `/api/news` 返回的 `processing_stats`：`candidate_by_date` 每天应大于 0，`processing_failed` 应明显下降

原因分析和量化模拟见 [数据接入诊断](数据接入诊断-20261104.md) 第二节。

## 六、同学拿到代码后怎么跑

```powershell
git clone https://github.com/zhixiny581-max/FinSight.git
cd FinSight
git checkout feature/ui-polish-20261104
```

1. 双击 `deploy/show-v2/打开配置文件.cmd`，从模板生成 `api-config.json`
2. 填两个必填项：`ifind`、`deepseek`（原样粘贴服务方给的值，不要自己加 `Bearer`）
3. 双击 `启动展示站.cmd`，进「工具 → 接口设置」点「全部检测」

不填也能启动，页面显示示例数据，只是接口卡片会标「未配置」。

只填自己有权限的项，`api-config.json` 已被 `.gitignore` 拦下，不会误传。
